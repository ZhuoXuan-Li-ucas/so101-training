# Gemini 336L 彩色相机接入与学习说明

这份文档面向第一次做机械臂实机项目的使用者。它说明当前这台 Gemini 336L 是怎样接入 LeRobot 的，也解释为什么选择这些参数、怎样自己重复验证，以及遇到问题时应该从哪里开始检查。

文中的设备编号和实测结果来自 **2026-10-12 的接入记录**。设备编号可能在重新插拔或重启后变化；实测结果也只代表当时的测试条件。文档中给出的命令可以帮助你重新检查当前状态。

本次完成的是：让 LeRobot 从 Gemini 336L 读取 **RGB 彩色图像**，并验证连续取图、保存照片和桌面实时预览。

| 项目 | 本次配置或结果 |

这次接入复用了现有环境。没有安装新依赖、切换仓库分支、修改系统驱动，也没有调整 USB 缓存。当前用户已经有彩色视频节点的读写权限，因此没有修改设备权限。

## 2. 先理解接入方式：Orbbec 后端与 OpenCV 后端有什么区别

### 2.1 “后端”是什么意思

在这里，“相机后端”可以理解为一层适配代码：上层 LeRobot 希望执行“连接相机、读取一张图像、断开连接”，后端负责把这些操作转换为具体设备能够理解的调用。

**Orbbec 是相机厂商的名称。** 教程里的 `orbbec_color`、`orbbec_depth` 是 LeRobot 相机配置中的类型名称，用于选择对应的彩色和深度适配代码。它们不是只能由教程作者使用的私有功能，个人开发者同样可以使用相应代码和 SDK。

本次查阅的 [Seeed 教程“添加摄像头”部分](https://wiki.seeedstudio.com/cn/lerobot_so100m_new/#添加摄像头)使用 `DepthCameraSupport` 分支提供 Orbbec 支持。接入时，本地仓库在 `main` 分支，没有注册这些 Orbbec 类型。因此，只把配置中的 `type` 改成 `orbbec_color`，并不会让当前仓库自动获得这个后端。

### 2.2 本次实际走的是哪条路径

当前相机的彩色通道可以通过 Linux 已有的视频接口读取，因此使用了以下链路：

```text
Gemini 336L 的彩色传感器
        ↓ USB 传输，格式为 YUYV
Linux UVC 驱动，提供 /dev/video* 设备节点
        ↓ V4L2 视频接口
OpenCV 读取图像
        ↓ LeRobot 的 OpenCVCamera 处理图像
RGB 数组，形状为 (480, 640, 3)
        ├─ 检查脚本：保存照片和统计读取速度
        ├─ 预览模式：把 RGB 数据交给 ffplay 显示
        └─ 后续录制程序：与机械臂状态、动作一起组成数据集
```

这条路径里的几个名词分别表示：

| 名词 | 在本次接入中的作用 |
| --- | --- |
| UVC | USB 视频设备使用的通用接口规范；本机已有的 `uvcvideo` 驱动识别了相机的视频接口 |
| V4L2 | Linux 向程序提供的视频设备访问接口 |
| OpenCV | Python 程序用来打开视频设备、读取和处理图像的库 |
| `OpenCVCamera` | LeRobot 对 OpenCV 相机读取功能的封装 |
| RGB | 图像按红、绿、蓝三个颜色通道表示 |
| ffplay | 用来显示视频画面的播放器；本次预览中，它接收脚本送来的 RGB 数据 |

对于目前“获取彩色画面，供机械臂录制与训练使用”的目标，这条路径已经具备需要的基本功能。它不仅用于显示一张测试照片，也使用了后续 LeRobot 能识别的相机配置。

### 2.3 哪些需求超出了这份 RGB 配置

如果以后需要获取每个像素对应的距离、把深度图与彩色图对齐、生成点云，或者调用特定设备功能，就需要进一步接入深度流和相应的设备接口。使用 Orbbec SDK 与匹配的 LeRobot 后端，是需要结合这些需求评估的路径。

深度接入还要确认图像格式、距离单位、内参、彩色与深度传感器之间的关系等。看到系统列出了深度视频节点，并不等于当前 RGB 配置已经提供了这些功能。

`pwd` 应显示仓库目录，`CONDA_PREFIX` 应显示 `/home/pangk/miniforge3/envs/lerobot-so101`。后两条命令用于确认当前终端能够找到 uv 和 ffplay。

后文使用这样的命令形式：


各部分含义如下：

| 命令部分 | 作用 |
| --- | --- |
| `uv run` | 通过 uv 启动程序 |

这能复用已经安装好的 LeRobot 环境，避免为一次相机检查重新同步整套项目依赖。它不表示首次安装环境时也可以跳过安装；这里的前提是当前环境已经准备完成。

命令中的反斜杠 `\` 表示“下一行仍然属于同一条命令”。复制时可以保留换行；反斜杠后面不要再添加空格或注释。

## 4. 怎样确认电脑识别到了相机

这一节按照“USB 设备 → 视频通道 → 支持的模式 → 稳定路径”的顺序排查。每一步回答的问题不同。

### 4.1 确认 USB 设备存在

```bash
lsusb
```

本次能够找到包含以下信息的一行：

```text
ID 2bc5:0807 Orbbec 3D Technology International, Inc Orbbec Gemini 336L
```

`2bc5:0807` 是 USB 厂商 ID 与产品 ID，不是这台相机的唯一序列号。它帮助确认连接的设备类型；区分具体哪一台相机要看序列号。

如果连这一步都找不到相机，应先检查连接线、USB 端口和设备供电状态。此时修改 Python 的相机编号通常不能解决问题，因为问题还在系统识别设备之前。

### 4.2 确认实际连接速度

```bash
lsusb -t
```

这条命令以树形结构显示 USB 设备和接口。本次相机相关接口显示 `5000M`，表示以 5 Gbps 的 USB 连接速度工作。这里是链路速度，不是脚本实际接收到的数据速度。

如果以后相同设备显示为 `480M`，说明当时工作在 USB 2 速度。可检查是否换了端口、线缆或集线器。这个结果本身并不证明当前低分辨率彩色流一定无法使用，但它意味着连接条件与本次测试不同。

### 4.3 找到视频设备节点

```bash
v4l2-ctl --list-devices
```

本次 Gemini 336L 对应 `/dev/video0` 到 `/dev/video7` 等视频节点。一台相机包含多个视频接口或元数据接口时，会出现多个节点，因此“看到八个 `/dev/video*`”并不表示有八台相机。

接入时已经确认：

- `/dev/video6` 提供彩色视频，支持 `YUYV` 和 `MJPG`。
- `/dev/video0` 列出了 `Z16` 深度格式。
- 其他节点不能仅凭编号推断用途，应查询各自的能力。

这些编号是当时的枚举结果。重新插拔、重启或增加其他相机后，应重新检查，不要把 `/dev/video6` 当成永久不变的名称。

### 4.4 查看某个节点支持的图像模式

接入时对彩色节点执行的是：

```bash
v4l2-ctl -d /dev/video6 --list-formats-ext
```

其中，`-d` 指定设备，`--list-formats-ext` 列出格式、分辨率和帧率组合。

本次彩色节点支持 `YUYV` 下的 `640x480`、`30 fps`，所以配置选择了这一组合。不要只分别确认“支持某种分辨率”和“支持某个帧率”；应该确认它们在所选格式下能够组合使用。

如果终端提示 `v4l2-ctl: command not found`，表示这个检查工具在当前终端不可用，并不能直接说明相机坏了。本次主机已有该工具，无需为了重复验证再次安装。

### 4.5 使用包含序列号的设备路径

```bash
ls -l /dev/v4l/by-id/
```

本次彩色通道对应：

```text
/dev/v4l/by-id/usb-Orbbec_R__Orbbec_Gemini_336L_CPCD7530003K-video-index0
```

它是一个符号链接，可以理解为系统为设备创建的另一个名称。下面的命令显示它当前实际指向哪个节点：

```bash
readlink -f /dev/v4l/by-id/usb-Orbbec_R__Orbbec_Gemini_336L_CPCD7530003K-video-index0
```

接入时输出为 `/dev/video6`。配置文件保存的是前面包含序列号的长路径，这样能减少对动态视频编号的依赖。

注意名称末尾的 `video-index0` 不等于 `/dev/video0`。它属于设备链接的命名，不是全系统视频编号。

换成另一台 Gemini 336L 后，序列号通常不同，需要重新检查并更新配置。固件或驱动环境改变后，也应重新确认该路径仍然指向需要的彩色通道。

## 5. 配置文件逐项说明

当前配置位于 [`gemini336l.json`](gemini336l.json)，内容如下：

```json
{
  "front": {
    "type": "opencv",
    "index_or_path": "/dev/v4l/by-id/usb-Orbbec_R__Orbbec_Gemini_336L_CPCD7530003K-video-index0",
    "width": 640,
    "height": 480,
    "fps": 30,
    "fourcc": "YUYV",
    "color_mode": "rgb",
    "backend": 200,
    "rotation": 0,
    "warmup_s": 2
  }
}
```

这份 JSON 是一组“相机名称 → 相机配置”的映射。它不是完整的机械臂录制配置，没有包含机械臂端口、校准文件、遥操作器或数据集信息。

| 参数 | 当前值 | 具体含义 |
| --- | --- | --- |
| `front` | 外层名称 | 给这路画面起的逻辑名称。名称本身不会改变相机的实际位置；后续 LeRobot 数据集通常使用 `observation.images.front` 表示这路图像 |
| `type` | `opencv` | 选择 LeRobot 已有的 OpenCV 相机后端 |
| `index_or_path` | 包含序列号的设备路径 | 指定读取哪一台相机的哪个通道 |
| `width` | `640` | 输出图像宽度，单位是像素 |
| `height` | `480` | 输出图像高度，单位是像素 |
| `fps` | `30` | 向相机请求的每秒帧数 |
| `fourcc` | `YUYV` | 选择相机视频流的像素格式；FourCC 指四字符格式代码 |
| `color_mode` | `rgb` | 要求 LeRobot 输出按红、绿、蓝排列的颜色通道 |
| `backend` | `200` | 当前 OpenCV 配置中的 V4L2 后端枚举值，用于 Linux 视频设备访问；它不是相机编号 |
| `rotation` | `0` | 软件不额外旋转图像 |
| `warmup_s` | `2` | 连接时先持续读取约 2 秒，让相机进入出图状态；不保证在所有光照条件下自动曝光都已完全稳定 |

### 5.1 YUYV 与 RGB 为什么会同时出现

它们描述的是图像在不同阶段的表示方式。

相机可以用 YUYV 格式通过 USB 传输数据，OpenCV 读取后进行转换，LeRobot 再按照 `color_mode: rgb` 输出 RGB 数组。因此，`fourcc: YUYV` 和 `color_mode: rgb` 并不矛盾。

在最终数组里，形状 `(480, 640, 3)` 的顺序是“高度、宽度、颜色通道数”。`uint8` 表示每个通道使用 8 位无符号整数，数值范围为 0 到 255。

### 5.2 本次为什么选择 YUYV

本次先验证了 MJPG 彩色取图。在一次重复连接中，MJPG 启动阶段出现了空帧解码警告。之后改用设备同样支持的 YUYV，并通过了连续取图验证，最终保存了这个配置。

这是针对这台主机和这次测试得到的选择，不表示 MJPG 在所有设备上都不可靠。MJPG 使用压缩传输，YUYV 使用未压缩的像素表示，它们的带宽和处理开销不同。

YUYV 平均每个像素占 2 字节，本配置的原始视频数据量约为：

```text
640 × 480 × 2 × 30 = 18,432,000 字节/秒
                       ≈ 18.4 MB/s
```

这里还没有计入 USB 协议等额外开销，也不是最终数据集视频的磁盘占用。转换后的 RGB 数组每个像素有 3 个字节，其内存数据量与 USB 上传输的 YUYV 数据量也不同。

当前 USB 3 单彩色流连接通过了实测。以后增加相机数量、启用深度或提高分辨率时，需要重新检查整体带宽和运行表现。

### 5.3 改配置时需要保持哪些一致性

分辨率、帧率和格式必须是该通道实际支持的组合。随意写一个数值，不会让设备自动具备这种模式。

开始录制一组训练数据后，应保持相机名称、视角、分辨率、图像方向和颜色处理一致。部署策略时也要提供与训练配置匹配的视觉输入。

随附检查脚本目前要求配置中只有一台名为 `front` 的 OpenCV 相机，并把 `index_or_path` 当作文件路径处理。它不是一个任意多相机检查工具。如果改名、增加相机或换成数字索引，需要同时检查脚本是否支持，不能只根据 LeRobot 通用配置的能力推断这个小脚本也支持。

## 6. 运行一次不带窗口的连续取图检查

### 6.1 完整命令

```bash
source /home/pangk/workspaces/so101-training/activate.sh
cd /home/pangk/workspaces/so101-training/lerobot

uv run --no-project --python "$CONDA_PREFIX/bin/python" \
  python examples/cameras/check_gemini336l.py --seconds 10
```

这条命令只打开相机，不连接机械臂。即使当前没有连接机械臂，也可以单独检查相机。

脚本先读取 JSON 配置，再连接设备并预热，之后开始统计读取。因此，从启动命令到退出的总时间通常长于 `--seconds` 指定的时间；解释器启动、连接、预热、保存文件和断开设备都会消耗时间。

### 6.2 脚本内部做了哪些事

1. 读取配置并交给 LeRobot 使用的配置解析器，确认类型与参数能够被识别。
2. 检查设备路径是否存在，并创建本次结果目录。
3. 通过 LeRobot 相机工厂建立 `OpenCVCamera`，连接设备并完成预热。
4. 使用 `async_read(timeout_ms=2000)` 重复获取图像。正常情况下会持续获得图像；如果等待下一帧超过约 2 秒，则会报超时，而不是将这次读取默认为成功。
5. 检查每次得到的数组形状是否与配置一致、数据类型是否为 `uint8`，并记录读取次数和时间间隔。
6. 正常完成后保存第一帧、最后一帧及统计报告，并释放相机资源。

这些检查能发现无法连接、取图超时、图像尺寸或数据类型不符合预期等问题。脚本不会自动判断取景是否合适、目标是否被遮挡、图像是否清晰，也不会计算相机硬件层面的精确丢帧率。

脚本执行中如果发生异常，代码会尝试清理相机和预览进程，但正常结束后的照片与报告可能不会生成。因此，出现一个结果目录不等于验证成功，应继续看终端输出和目录内文件。

### 6.3 怎样理解正常输出

下面是一次成功运行的输出示例，时间目录会随每次运行变化：

```text
Connecting to /dev/v4l/by-id/...-video-index0 -> /dev/video6
Received 301 RGB frames, measured read rate 29.95 FPS.
Snapshots and report saved in: .../outputs/gemini336l/20261012-100328-055648
Camera released. You can now open a preview or use the camera in LeRobot.
```

第一行显示配置使用的设备路径和当时实际指向的节点。第二行显示脚本读取到的帧数和平均读取速度。第三行告诉你本次结果放在哪里。最后一行表示脚本已完成设备释放，可以继续运行其他相机程序。

### 7.1 预览命令

在主机本地桌面的终端执行：

如果不提前退出，脚本正常情况下会在指定的取图时长结束后关闭窗口。这个时长不包括启动、预热和清理时间，也不是进程在异常情况下的严格超时上限。

预览正常结束、并且已获得足够帧数时，也会保存首尾照片和报告。若刚启动便关闭窗口，尚未取得至少两帧，脚本可能提示没有足够帧数用于统计。

### 7.2 为什么不直接调用 `cv2.imshow`

当前环境使用的是 OpenCV headless 版本。它可以读取、转换图像，但不提供 `cv2.imshow` 所需的桌面窗口功能。

为了复用当前环境，脚本让 LeRobot 负责取图，把解码后的 RGB 字节通过进程管道发送给已有的 ffplay，由 ffplay 打开窗口显示。这里的“管道”是本机进程之间传递数据的方式，不是网络上传。

本次还测试过让 ffplay 直接打开相机的 V4L2 设备，但它停在了启动空包阶段。因此随附脚本采用了“LeRobot 取图 → ffplay 显示”的方式，并完成了预览验证。这是本机实际遇到的情况，不意味着所有机器上的 ffplay 都不能直接打开此型号相机。

### 7.3 预览与正式取图的测试结果为什么可能不同

打开预览后，主线程除了获取图像，还要向显示进程写入数据。窗口启动和显示处理会引入额外等待，所以预览模式的读取速度和最大间隔可能与不带窗口时不同。

因此，检查基础取图速度时先看不带 `--preview` 的结果；检查构图、方向和光照时再看预览。两种检查各自回答不同的问题。

预览需要可以使用的桌面显示环境。如果从没有图形显示的远程终端运行，先使用不带 `--preview` 的检查命令并查看保存的 PNG；窗口打不开本身不能证明相机取图失败。

### 8.2 各个字段具体表示什么

| 字段 | 怎样理解 |
| --- | --- |
| `captured_at` | 生成报告时的本地时间，包含时区；不是每帧的硬件曝光时间戳 |
| `config` | 本次使用的原始相机配置，便于以后确认参数是否发生变化 |
| `resolved_device` | 序列号路径在本次运行时实际指向的设备节点 |
| `opencv_version` | 本次环境中的 OpenCV 版本 |
| `frames_received` | 脚本的取图循环成功得到的图像次数，不包括连接阶段的预热读取 |
| `measured_interval_seconds` | 第一次成功读取到最后一次成功读取之间的时间跨度 |
| `measured_read_fps` | 根据上述读取次数与时间跨度算出的平均读取速度 |
| `max_read_interval_ms` | 相邻两次成功读取之间的最大时间间隔，单位为毫秒 |
| `frame_shape` | 最后一张图像的数组形状，按“高、宽、通道”排列 |
| `frame_dtype` | 图像数组的数据类型 |
| `frame_mean` | 最后一帧所有通道数值的平均值，可粗略辅助观察整体明暗 |
| `frame_std` | 最后一帧数值的标准差，可粗略辅助观察图像数值变化程度 |
| `camera_disconnected` | 脚本清理后，该相机对象是否已断开；不代表系统中不存在其他相机进程 |

`frame_mean` 和 `frame_std` 不能作为画面质量是否合格的自动判断依据。例如，正常的白墙画面与异常画面都可能具有较小的数值变化，仍需直接查看照片。

### 8.3 “设置 30 FPS”和“实测 29.95 FPS”分别说明什么

配置中的 `fps: 30` 是向设备请求的流参数。报告里的读取帧率来自 Python 程序实际收到图像的时刻，计算方式是：

```text
平均读取帧率 = (收到的帧数 - 1) / (最后一次读取时刻 - 第一次读取时刻)
```

301 帧之间有 300 个相邻时间间隔，因此公式使用 `301 - 1`，而不是直接使用 301。

LeRobot 的后台线程持续读取图像，`async_read` 获取可用的新图像，但不是一个保证把全部硬件帧逐一交给主线程的永久队列。主线程变慢时，中间图像可能已经被更新的图像替换。

因此，接近 30 FPS 说明本次主线程总体上能以接近目标的速度得到图像；它不能单独证明每一张硬件帧都被保留、完全没有间隔抖动，或图像已与机械臂动作精确同步。脚本也没有把所有日志警告或设备丢帧计数写入报告。

### 8.4 这份检查报告不是训练数据集

训练用的数据集还需要按任务组织 episode，并把相机图像、机械臂状态、示范动作以及任务信息等关联起来。这里保存的两张 PNG 和一个 JSON 只是相机验证结果，没有这些完整信息。

下一步需要通过实际的 LeRobot 录制流程生成数据，而不是把这个测试输出目录直接作为训练数据集使用。

## 9. 怎样把相机配置接到后续 LeRobot 录制中

### 9.1 添加或替换 `--robot.cameras` 参数

当你已经有一条适合当前机械臂的 `lerobot-record` 或 `lerobot-teleoperate` 命令时，把其中的相机参数替换为下面的内容。

**下面是参数片段，不能单独作为命令执行：**

```bash
--robot.cameras="$(cat examples/cameras/gemini336l.json)"
```

这个写法要求当前目录是本仓库。也可以使用绝对路径，避免终端所在目录变化的影响：

```bash
--robot.cameras="$(cat /home/pangk/workspaces/so101-training/lerobot/examples/cameras/gemini336l.json)"
```

保留你已经确认的机械臂类型、端口、校准 ID、遥操作器和数据集设置。如果原命令已有 `--robot.cameras`，应替换该参数，不要在同一条命令里再追加一份重复参数。

这个片段会把文件中的整组相机配置传进去。如果你原来配置了其他相机，而新文件里只有 `front`，直接替换会只保留这一台。因此，多相机录制需要先整理完整配置，不能把当前单相机文件直接当作多相机配置使用。

### 9.2 `$(cat ...)` 到底在做什么

执行命令时，Shell 先运行括号里的 `cat` 读取 JSON 文件，再把文件内容放进 `--robot.cameras` 的参数值中。外层双引号使包含空格和换行的整段 JSON 作为一个参数传递。

不要把外层双引号换成单引号，否则 `$(cat ...)` 会被原样当作文字传入，不会读取文件。

JSON 文件里保存的是相机参数，不包含连接设备的程序。它会在下一次程序启动、读取配置时生效；修改文件不会自动改变一个已经运行中的相机进程。

### 9.3 正式录制前需要确认的对应关系

- **名称对应**：这里相机名为 `front`，后续数据集与策略配置应保持相同名称。改名后，模型寻找的输入字段也可能需要随之调整。
- **帧率对应**：相机的 `fps` 与录制程序的数据集帧率是两个配置位置。当前仓库的数据集默认帧率为 30，可通过 `--dataset.fps` 设置；应检查实际录制命令与相机供图能力是否匹配。
- **画面对齐到任务**：确认夹爪、目标和放置区域都在画面中，再开始录制示范。
- **设备可用**：退出独立预览和检查脚本后，再启动录制程序，避免两个程序同时占用同一路相机。
- **验证实际录制结果**：录制一小段实际示范后，检查保存的数据里是否有正确的 `front` 图像，以及图像与动作是否相符。相机独立检查不能替代这一步。

这里不直接提供带机械臂端口的完整执行命令，因为相机配置不会替你确定当前主从臂端口与校准 ID。完整的机械臂运行命令应基于已经验证的硬件配置编写。

## 10. 怎样摆放相机，让图像对训练有用

本次保存的测试照片主要拍到了室内环境，证明相机能够出图，但还不是机械臂操作任务所需的视角。

先启动预览，观察画面能否同时覆盖夹爪、待抓取物体和目标放置区域。随后结合实际任务检查物体接触、夹取、搬运和放下的位置是否可见。只看到机械臂外观，却看不清物体与夹爪接触关系，会增加后续学习任务的难度。

对于固定视角的数据采集，把相机和支架固定牢靠，并记录大致位置、方向和高度。采集过程中相机意外移动会改变图像与机械臂工作区域的对应关系；如果确实调整了视角，应把它作为数据条件变化来处理。

光线应让目标物体轮廓和夹爪动作能够被看清。预览时留意明显的反光、背光、阴影和运动模糊。提高图像分辨率不能自动弥补不合适的机位或光照，因此先把画面内容调整正确，再评估是否需要更高分辨率。

调整完毕后，关闭预览，再运行一次不带窗口的检查，保存新的确认照片。这样以后可以对照照片判断机位是否发生变化。

## 11. 常见问题：按现象逐步检查

### 11.1 提示 `Camera not found`

先检查 USB 层是否还能看到设备：

```bash
lsusb
ls -l /dev/v4l/by-id/
```

如果 USB 列表中没有相机，先检查连接。如果 USB 设备存在但原来的长路径不存在，可能是换了相机、视频接口尚未建立或链接名称发生变化。重新检查节点和支持格式后，再更新 JSON 中的路径。

不要为了消除错误随意改成 `/dev/video0`。本次这个编号对应深度通道，不能直接拿来代替已验证的彩色通道。

### 11.2 提示权限不足，或设备存在但打不开

先查看设备权限和当前用户信息：

```bash
id
ls -l /dev/video6
getfacl /dev/video6
```

如果设备编号已经变化，应把上面的 `/dev/video6` 替换为 `readlink -f` 查询到的实际节点。

Linux 的设备访问可能由组权限或 ACL 授权。接入时，当前用户通过 ACL 已有彩色节点的读写权限，即使用户组列表中没有 `video`，也能成功读取。

所以应该依据实际权限判断问题，不要只因为某个组名缺失，就推断一定不能使用相机。本次无需给全部 USB 设备放开权限，也无需把整个 Python 相机程序改为以 root 运行。

### 11.3 提示设备忙、连接失败或等待图像超时

先关闭你已经打开的相机查看器、独立预览或录制程序。也可以检查当前节点是否被占用：

```bash
fuser /dev/video6
```

这条命令只查询占用进程，不会终止它们。如果返回进程编号，先确认它属于哪个程序，并从该程序正常退出。无输出时还需结合命令权限和其他现象判断，不能把一次查询当作所有故障的最终结论。

设备占用只是可能原因之一。仍然超时时，继续检查路径、格式组合、USB 连接及终端中的第一条报错。不要只看最后出现的超时异常。

### 11.4 提示无法设置宽度、高度、帧率或 FourCC

查询实际设备能力：

```bash
v4l2-ctl \
  -d /dev/v4l/by-id/usb-Orbbec_R__Orbbec_Gemini_336L_CPCD7530003K-video-index0 \
  --list-formats-ext
```

对照配置里的 `fourcc`、`width`、`height`、`fps`，确认整个组合受支持。本次已经验证的组合是 YUYV、640×480、30 FPS；先复用这个组合，再考虑逐项调整。

如果路径指向了错误通道，即使相机型号相同，也可能完全不支持这组参数。

### 11.5 出现 `imdecode` 或空帧相关警告

本次 MJPG 重复连接时出现过启动空帧解码警告，最终选择 YUYV 完成验证。如果自己修改过 `fourcc`，先核对当前配置是否仍是文中的 YUYV。

短暂启动警告与持续无法出图应分开判断。前者需要结合后续图像和读取结果观察，后者应继续排查设备占用、模式、线缆和连接。出现警告不能直接推断相机硬件损坏；正常退出也不能抹去中途出现过的警告。

### 11.6 能保存照片，但预览窗口打不开

先运行不带 `--preview` 的检查。如果照片能够正常生成，说明相机取图链路至少可以工作，接下来重点检查显示环境。

```bash
command -v ffplay
printf '%s\n' "$DISPLAY"
```

`ffplay` 找不到时，先确认是否激活了 `lerobot-so101` 环境。没有可用桌面会话的远程终端通常不能直接打开本地主机的预览窗口。

本环境的 OpenCV 为 headless 版本，因此通过报错去反复调用 `cv2.imshow` 不能解决窗口问题。使用文中的 `--preview` 路径，或在无桌面环境下查看保存的照片。

### 11.7 实测帧率偏低、图像卡顿或最大间隔变大

先区分是只有预览卡顿，还是无窗口取图也慢。关闭预览，使用相同参数重新检查，能减少显示过程对主线程的影响。

随后对照 USB 速度、是否增加了其他相机、是否提高了分辨率，以及主机是否正在进行训练等高负载任务。每次只改变一个条件，并对照新的 `report.json`，才能较容易判断哪项变化影响了结果。

只看平均 FPS 可能漏掉短时停顿，因此也要查看最大读取间隔和实际画面。不过，本脚本没有保留每个间隔的完整分布，也不提供设备级丢帧计数，不能承担完整性能分析工具的作用。

### 11.8 配置解析失败，或者提示只能有一台 `front` 相机

JSON 要使用双引号表示字符串，不能添加普通注释，也不能在最后一个字段后保留多余逗号。

在已激活环境、本仓库目录下，可以只检查 JSON 语法，不打开相机：

```bash
uv run --no-project --python "$CONDA_PREFIX/bin/python" \
  python -m json.tool examples/cameras/gemini336l.json
```

JSON 语法正确后，还需要满足脚本自身的限制：只配置一个名为 `front` 的 OpenCV 相机，且设备使用有效路径。这个限制来自随附检查脚本，不表示 LeRobot 本身只能配置一台相机。

### 11.9 中途退出后没有照片或报告

正常结束或正常关闭预览后，脚本会在清理设备之后保存结果。如果使用 `Ctrl+C` 中断、发生取图异常或读取帧数不足，脚本可能只留下已创建的目录，而没有生成正常结果文件。

先看终端报错并解决问题，再重新运行一次完整检查。不要把空目录当作一次成功记录，也不要把更早时间目录里的照片误认为这次运行的结果。

## 12. 后续复习时可以按这个顺序阅读

如果只是想确认相机还正常，按第 3 节进入环境，再执行第 6 节的检查命令。

如果要调整机位，使用第 7 节预览，结合第 10 节确认画面内容。调整后保存一次新的检查结果。

如果要接入正式录制，先理解第 5 节参数，再按第 9 节把相机配置合入已有的机械臂命令，并验证实际录制的数据。

如果要学习源码，可以从这些文件开始：

- [`check_gemini336l.py`](check_gemini336l.py)：本次检查、统计、保存和预览逻辑。
- [`gemini336l.json`](gemini336l.json)：当前这台设备的参数。
- [`configuration_opencv.py`](../../src/lerobot/cameras/opencv/configuration_opencv.py)：OpenCV 相机支持哪些配置字段。
- [`camera_opencv.py`](../../src/lerobot/cameras/opencv/camera_opencv.py)：连接、后台读取、颜色处理和资源释放。
- [`cameras/utils.py`](../../src/lerobot/cameras/utils.py)：LeRobot 怎样根据配置创建相机对象。
- [`lerobot_record.py`](../../src/lerobot/scripts/lerobot_record.py)：正式录制流程怎样获取观察并保存数据。
- [Seeed 教程“添加摄像头”](https://wiki.seeedstudio.com/cn/lerobot_so100m_new/#添加摄像头)：对照理解专用相机分支和本次通用彩色接入路径。
